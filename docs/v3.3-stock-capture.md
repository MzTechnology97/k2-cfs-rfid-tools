# v3.3 stock-task Bambu capture

v3.3 is the first K2 CFS RFID build I validated end-to-end with a real Bambu Lab spool.

Unlike my earlier direct diagnostic RF experiments, API7 leaves RF ownership with Creality's stock RFID manager. The host derives the Bambu Key A from the tag UID, arms a one-shot three-key override, and then asks the normal CFS driver to perform the standard force-read operation. The firmware wrapper substitutes the keys only at the original stock authentication calls and captures the successful legacy read result into scratch storage.

## Data flow

```text
K2-OpenHost / CM5
  -> read stock internal UID
  -> derive Bambu sector-1 Key A
  -> API7 ARM_KEYS3
  -> normal CFS force_rfid_read()
  -> Creality stock RFID task
  -> original auth/read calls with temporary Key A
  -> capture block 4 + block 5 RGBA into scratch
  -> CM5 reads scratch and decodes material + colour
  -> CLEAR_KEYS
```

The three stock legacy reads are for blocks 4, 5 and 6. They are all in MIFARE Classic sector 1, so the same derived sector-1 Key A is armed three times.

## Captured data

API7 intentionally captures only enough data to identify the spool preset and colour: all 16 bytes of block 4 plus the first four bytes of block 5.

I initially expected the stock CFS `CMD_RFID_REMAINING (0x03)` path to remain authoritative for Bambu spools, but hardware testing disproved that assumption. On Bambu API7 spools the CFS can return `0xFF` for the slot, which means the stock remaining value is unavailable. Historical testing of PLA Matte and current tests of PETG HF / PETG Basic all show this behaviour.

I therefore do not treat the stock CFS remaining value as valid for non-Creality tags. I am separately reverse-engineering the stock RAM-only odometer/remaining tracker so it can potentially be initialized for third-party tags without writing those tags.

## Compatibility

I validated this implementation specifically on `cfs0_050_G32` / `cfs0_000_153`. The current host implementation refuses the API7 stock-capture path when runtime inspection reports the secure backend because result capture has only been validated for the legacy backend.

## Result

On 2026-10-07 my K2 Pro successfully identified a Bambu `PLA Matte` spool with UID `233A111D` and colour `#FFFFFF`, first through a manual API7 read and then through the automatic Creality-unknown -> Bambu-fallback path.
