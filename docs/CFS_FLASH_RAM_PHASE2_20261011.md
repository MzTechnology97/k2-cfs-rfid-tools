## Physical MCU vs Creality application (critical distinction)

Chip *assumption* GD32F303VET6 must be corroborated by board silkscreen/marking
or authenticated CFS silicon identification. Official vendor product page
[GD32F303VET6](https://www.gigadevice.com.cn/product/mcu/mcus-product-selector/gd32f303vet6)
and the GD32F30x reference manual distinguish the first **256 KiB of Flash
with fast instruction fetch** from the further **256 KiB with slower instruction
fetch**. Instructions can be fetched beyond the first 256 KiB, but execution
latency is higher; the split does **NOT** mark the latter half non-executable.
The part has **64 KiB SRAM** and uses a **Cortex-M4**.
See the GD32F30x User Manual §2.1-2.3
(https://www.gd32mcu.com/data/documents/userManual/GD32F30x_User_Manual_Rev2.9.pdf). Legacy
`-mcpu=cortex-m3` test builds use a subset of Thumb instructions and are
byte-identical to the currently installed image, but do *not* prove that a
future FPU/context-switch instrumentation is ABI-safe.

| Region / invariant | Range or value | Confidence |
| --- | --- | --- |
| Physical MAIN Flash (conditional on exact silicon) | `0x08000000..0x0807FFFF` (512 KiB) | vendor silicon total capacity, not loader authorisation |
| Faster code fetch region | `0x08000000..0x0803FFFF` (first 256 KiB) | performance threshold, **not execution ban** beyond it |
| Firmware application link base | `0x08010000` | verified image/vector |
| Lower 64 KiB before application | `0x08000000..0x0800FFFF` | *contents not dumped*; consistent with loader, not proof |
| Original app153 end (exclusive) | `0x0803AE38` | SHA/CRC/length pinned |
| Working v3.22 end (exclusive) | `0x0803B7DC` | SHA/CRC/length pinned |
| Conservative build-policy boundary | `0x0803B800` | **UNVERIFIED**, NOT a bootloader-certified limit |
| Remaining bytes below that arbitrary policy boundary | **36 bytes** | arithmetic only |
| Bytes until 256 KiB **fast-fetch boundary** | **18,468 bytes** | **NOT free or approved for use** |
| Bytes to full 512 KiB silicon Flash end | **280,612 bytes** | **NOT free or approved for use** |
| Unflashed `sizeopt2` comparison | 178,120 bytes; 56B to old policy bound | experimental; not regression/boot validated |
| Loader max accepted image / erase map / last reserved page | **UNKNOWN** | release blocker |

Why neither of the 18,468-byte / 280,612-byte theoretical gaps is **approved usable headroom**:
there is no bootloader dump, no authoritative app-length limit, and no proof
that `0x0803B800..0x0803FFFF` lacks sector state, calibration, configuration,
recovery metadata or CFS-specific loader reservation. The slower-fetch second 256 KiB of Flash may be physically executable,
but relocating code there would require loader support, verified links,
latency profiling and interrupt/timing regression. Do not equate the
datasheet's CODE/DATA access categorisation with an execute-permission bit.
Aligned four-byte scans show no literal word directly in the suspected
`0x0803B800..0x0803FFFF` range, but that is **not absence-of-use proof**
(computed addresses, pointer arithmetic, instructions and loader code are
invisible to this simple scan).

Existing read-only host-tool recovery analysis independently established that
the updater transmits application size and chunks **without a host-selected
destination flash address**. A previously observed G32 loader sector token
`0xE0` determines an **RS-485 transfer chunk of 128 bytes**, *not* the
flash erase-page size or maximum application length.
See `k2-openhost-firmware-tools/docs/CFS_RECOVERY_ANALYSIS.md` on the
authorised CM5 for exact scope. A complete loader layout must be recovered
from an independently acquired bootloader image, manufacturer/Creality
memory script, or genuinely read-only debug access. **Do not enter loader
mode on the reference CFS merely to read a token**: that operation
changes device state and needs separate authorisation.

## Erase page implications

The GD32F30x HD / bank0 **2 KiB erase-page geometry** makes the historical
`0x0803B800` threshold the start of 2 KiB page **119** (zero-based).
The v3.22 image ends at `0x0803B7DC`, inside page **118**
(`0x0803B000..0x0803B7FF`), leaving 36 bytes until page 119.
The first 256 KiB runs through page 127: **pages 119–127 are nine
undocumented 2 KiB pages (18,432 bytes)**. Their function or reservation
cannot be inferred from this coincidence alone. The 128-byte `0xE0`
host transport chunk is **not** a 2 KiB erase page.

## SRAM geometry

| Evidence | Address/size |
| --- | --- |
| GD32F303VE SRAM (conditional on silicon identity) | `0x20000000..0x2000FFFF` = 64 KiB |
| Initial MSP vector from both original and v3.22 | `0x20006EE8` |
| Existing volatile CFS sidecar | `0x20006EE8..0x20006F27` = 64B |
| Actual heap-base literal in working v3.22 image | `0x20006F28` |
| Heap top literal | `0x20010000` |
| Current **nominal**, not measured, heap span | **37,080 bytes** |
| Proposed, NOT allocated v3.23 RAM event ring | `0x20006F28..0x20007127` = 512B |
| Proposed, NOT patched new heap start | `0x20007128` (8-byte aligned) |
| Hypothetical nominal heap after ring reservation | **36,568 bytes** |
| Relative heap reduction | **1.381%** |

The initial MSP is the **stack ceiling at reset**, *not* measured minimum
stack. The bare address map does not identify all RTOS tasks, heap
high-water, DMA buffers, interrupt nesting, or concurrent ring writers.
The proposed ring overlaps the **current live heap by definition** until
the allocator is moved, so it cannot be used without invasive validation.
The observed four Thumb instruction encodings resembling `0x200070xx`
are known **false positive 32-bit little-endian word scans**. The fifth
ring-range word is the known current heap pointer. See existing v3.23
`heap_static_crosscheck.py`; neither test detects indirect RAM pointers.

## Correction to the earlier dead-code hypothesis (2026-10-11)

**Do not delete `config_v2_ensure`: it is live via a symbol alias.**
The assembly defines:

```asm
config_v2_ensure:
config_ptr:
    ldr r0, config_root_ptr
    ...
```

The label `config_ptr` points to the same address `0x0803AF72`.
Elsewhere `config_v2_get_value` includes `bl config_ptr`. A text-only
grep for the name `config_v2_ensure` had wrongly suggested no calls.
The ~20B routine and both `config_root_ptr` / `config_expected_ptr`
MUST be preserved. The earlier statement about their potential removal
is hereby withdrawn.

The historical six-byte speed table `config_defaults` is a different
case: it has no direct named reference in the assembler. In a **private,
isolated, never-flashed test**, deleting only this table and rebuilding
the complete v3.22 application reduced the image from **178,140** to
**178,136 bytes**. The real saving was **4 bytes**, not 6, because of
ARM alignment. Isolated full-image Unicorn tests of 28 GET values,
21 advanced SET/GET/RESET paths, busy state rejection and the two
effective timing hooks passed. The independently tested candidate has
SHA256 `a743f747a11528a1cc4f3b6d31296560946723db7ac9eb5769974a421ad3c1d0`
and has **NOT been flashed or released**.

This small optimization is not a credible way to accommodate the
proposed ~320B event logger plus trampoline and transport. The
pre-existing separate 178,120-byte sizeopt experiment also modifies
branch widths and response serialization; its savings must not be
combined with these four bytes. Neither candidate is approved for
the operational CFS. The hardware-proven reclaimable budget remains
**zero bytes**.

See `docs/CFS_DATABASE_XREF_AND_SIZEOPT_20261011.md` and
`firmware/v3.22-readonly-state-probes/database_path_and_sizeopt_audit.py`.
The original firmware is still byte-identical and untouched.

## Repeatable test procedure

```bash
python3 firmware/v3.22-readonly-state-probes/flash_ram_phase2_audit.py \
  --stock /private/cfs0_000_153-unmodified.bin \
  --v313 firmware/v3.19-volatile-ram/cfs0_050_G32-cfs0_000_153-runtime-config-v3_13.bin \
  --v322 /private/CFS-v322-verified.bin \
  --asm firmware/v3.22-readonly-state-probes/handler-v3_22.S \
  --self-test --json-out /tmp/FLASH_RAM_PHASE2_EVIDENCE.json
```

The script checks exact 4 image fingerprints (if the optional sizeopt
image is included), application length and CRC16, vector validity,
heap literals, RAM bounds, and four deliberate corruption mutations.
All four fingerprinted images and the four mutation tests pass on the
isolated authorised CM5 checkout. It never flashes, modifies BIN/ELF
or opens a serial device.

The existing `v3.23-ram-event-trace/heap_static_crosscheck.py` and
ARM/Unicorn ring tests provide extra **static/offline** evidence but
do not close the following release gates.

## Before any new firmware image may be proposed

1. Authenticate the actual microcontroller silicon variant and obtain a
   verifiable *loader/application partition and reserved-page map*.
2. Confirm actual application maximum size and erase-page ownership;
   retain the conservative bound and flash disabled until then.
3. Instrument or otherwise prove runtime heap peak/fragmentation,
   per-task stack high-water, DMA and IRQ memory ownership.
4. Prove entire motor start/stop transition coverage, atomic safety
   checks, arm Thumb ABI/flags/latency and ring writer ownership.
5. Complete hardware regression on both original Creality spool and
   third-party RFID (raw captures, UID guards, minimum rotations,
   geometry/remaining, load/unload and timeout paths).
6. Retain separate Kalico motion/RFID lock and reject fake 9–27
   tuning IDs, including raw-serial bypass risks.

**Current action: none of these conditions authorises a v3.23 flash.**
