# v3.12 stock-geometry remaining for third-party RFID

This document records how I made the stock CFS remaining-filament mechanism work with a third-party API7 capture.

## What I wanted

I did not want to estimate remaining filament on the CM5 from Bambu metadata. My goal was to reuse the same approximate mechanism Creality already uses:

```text
CFS rotates spool
-> CFS estimates spool geometry
-> CFS maintains remaining in RAM
-> CMD 0x03 returns one byte per slot
```

That also explains why I stopped trying to remove every RFID rotation: some of the rotation is part of the stock geometry measurement.

## Stock data I recovered

The stock percentage table is:

```text
slot 0  0x20003974
slot 1  0x20003975
slot 2  0x20003976
slot 3  0x20003977
```

The stock setter is:

```text
0x080123E4(slot, percent)
```

The stock type-4 runtime base is:

```text
0x20004590 + 100 * slot
```

The stock initializer is:

```text
0x0801AA14(slot, initial_percent)
```

I also recovered a genuine Creality RFID record with `len=0330`, which the stock code converts to 330000 mm.

## Why the first remaining experiments failed

The development sequence was useful because each failed candidate exposed another stock gate.

### v3.8

I hooked the remaining initializer and tried to seed type 4 with the stock geometry percentage.

The problem was that third-party tags could receive `0xFF` instead of the calculated percentage before my hook.

### v3.9

I recovered the percentage directly from `0x20003974 + slot` when the initializer argument was `0xFF`.

This still did not run because the stock global gate at `0x08013380` could skip the initializer completely.

### v3.10

I wrapped the gate and allowed it to continue only after a complete third-party API7 capture.

This still returned `0xFF`.

### v3.11

I discovered a timing issue: Kalico reads the API7 capture and sends `CLEAR_KEYS` after `force_rfid_read()` returns.

I tested a post-clear `K2RL` latch. The latch was visible in CFS RAM, but it was created after the stock geometry/remaining phase had already run.

### v3.12

I moved the latch into the stock RFID task itself.

Immediately after the third authenticated read succeeds, before the stock task continues into geometry processing, I:

```text
complete API7 masks/capture
-> disarm temporary keys
-> write K2RL into scratch
-> continue stock state machine
```

The later remaining gate recognizes this transient latch for the current logical slot.

That was the missing ordering constraint.

## v3.12 flow

The successful path is:

```text
API7 ARM
-> Creality stock RFID worker
-> blocks 4/5/6 authenticate and read
-> third read succeeds
-> K2RL pre-geometry latch
-> stock spool geometry calculation
-> area_percent stored at 0x20003974 + slot
-> stock global gate
-> guarded third-party continuation
-> recover area_percent if stock passed 0xFF
-> initialize type-4 runtime with 330000 mm
-> stock remaining setter
-> consume K2RL
-> CMD 0x03 returns 0..100
```

Normal Creality reads still take the original stock branch.

## Hardware validation

On my K2 Pro with a Bambu PETG HF spool I measured:

```text
CMD 0x03 payload = 0CFFFFFF
Bambu slot       = 12%
```

The existing Kalico path then exposed:

```text
rfid_reported_percent  = 12
rfid_percent           = 12.0
rfid_estimated_percent = 12.0
```

I did not modify the Kalico remaining implementation to obtain this result.

For regression testing I reread a genuine Creality RFID spool:

```text
CMD 0x03 payload = FF21FFFF
Creality slot    = 33%
```

The same spool had returned 38% on an earlier geometry scan, so I treat this mechanism as an approximate fill estimate, exactly as intended.

## Detailed stock map I recovered

For reference, these are the stock-1.5.3 structures and functions I used to build the final implementation.

### CMD 0x03 path

The stock dispatcher handles the remaining query at:

```text
dispatcher branch      0x0801C3C0
reply builder          0x0801BF66(mask)
final getter           0x080123CE(slot)
remaining setter       0x080123E4(slot, percent)
```

The reply starts with all four bytes set to `0xFF`. A slot is replaced with a percentage only after the stock validity path accepts it.

### Stock remaining table

The per-slot database base is:

```text
0x2000391C
```

The current remaining bytes are:

```text
slot 0  0x20003974
slot 1  0x20003975
slot 2  0x20003976
slot 3  0x20003977
```

The stock setter clamps zero to one before storing the byte.

### Stock RFID record

The 40-byte Creality record begins at:

```text
0x2000391C + 0x5C + 40 * slot
```

The stock record setter is:

```text
0x08012444(slot, record40)
```

The validity helper used by the remaining path is:

```text
0x0801245C(slot)
```

I recovered this genuine record from my K2 Pro history:

```text
AB1240276A21056280B1BEC60330000001000000
```

The parsed fields are:

```text
month       offset 0   len 1
day         offset 1   len 2
year        offset 3   len 2
supplier    offset 5   len 4
batch       offset 9   len 2
mat_id      offset 11  len 6
color       offset 17  len 7
len         offset 24  len 4
number      offset 28  len 6
reserve     offset 34  len 6
```

The `len` field is `0330`, which is the source of the 330 m nominal reference I use in v3.12.

The same record also exists inside the 76-byte internal record at offsets `20..59`; the length is therefore at `INTERNAL_RECORD[44:48]`.

### Runtime odometer

The stock runtime base is:

```text
0x20004590
```

with a stride of 100 bytes per slot:

```text
runtime(slot) = 0x20004590 + 100 * slot
```

Important fields I traced include:

```text
+0   used counter
+20  initial percent
+23  valid/active flag
+40  status/error
+99  runtime type
```

The stock initializer is:

```text
0x0801AA14(slot, initial_percent)
```

For a normal Creality record it copies the internal metadata, sets the initial percentage, clears the usage counter, marks the runtime valid, parses the ASCII length and stores the nominal total in millimetres.

### Type 4 versus type 7

The stock type-4 path computes the remaining percentage approximately as:

```text
used_percent = used_mm * 100 / total_mm
remaining    = initial_percent - used_percent
```

I found no RFID tag-write call in this type-4 path, which is why I selected it for third-party spools.

The type-7 path is different: the stock binary contains the diagnostic string:

```text
rfid write used=%dmm,percent=%d: find=%d,write=%d,error=%d
```

I intentionally do not use type 7 for Bambu/QIDI because I want the third-party path to remain tag-read-only.

## What I am not claiming

I have hardware-validated the new remaining path on Bambu.

I have already hardware-validated QIDI PET-CF material identification through API7/generic MIFARE, but I have not yet repeated the v3.12 remaining validation on that QIDI spool. I therefore do not claim QIDI remaining as hardware-validated yet.

I also do not claim that 330 m is the physically correct length for every third-party material. It is the stock Creality reference I intentionally chose for a consistent approximate odometer model.

## Safety

The v3.12 path is RAM-only for third-party remaining.

I do not call the stock MIFARE write primitive and I do not call the EEPROM write primitive. The tag remains read-only.
